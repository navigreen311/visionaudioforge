# Pinned versions are the ones the backend suite is verified against.
#
# Two classes of problem were found in the previous set and are called out
# where they occur below: pins carrying published vulnerabilities (112
# advisories across 11 packages, per pip-audit), and pairs that resolve
# cleanly but cannot work together at runtime — pip cannot see the second
# kind, so only running the code finds them.

# Web framework
# starlette 0.36.3 (which fastapi 0.109 pins) carries nine advisories,
# including denial of service via multipart parsing, so fastapi and pydantic
# move together.
#
# fastapi is held at 0.136 rather than the latest: from 0.139 an included
# router is wrapped in a private `_IncludedRouter` and no longer flattened
# into `app.routes`. Routing still works, but every caller that *enumerates*
# routes sees an almost empty table — which is app/services/plugins/
# api_docs.py, and the auth-enforcement sweep that walks the routing table to
# prove no endpoint serves anonymous callers. That sweep would have passed
# while testing nothing. 0.136 keeps the flat table.
#
# starlette is pinned directly because 0.136 asks only for `>=0.46.0`, and the
# published fixes run to the 1.x line.
fastapi==0.136.0
starlette==1.6.0
uvicorn[standard]==0.52.3
pydantic[email]==2.13.4
pydantic-settings==2.15.0

# Auth
# 3.3.0 carried CVE-2024-33663 (algorithm confusion: an OpenSSH ECDSA public
# key can be used to sign a token that verifies) and CVE-2024-33664 (a JWE
# decompression bomb). Both fixed in 3.4.0. Tokens are the whole of our
# authentication, so this is not a pin to leave sitting.
python-jose[cryptography]==3.5.0
# python-jose pulls `ecdsa` unconditionally, and ecdsa 0.19.2 — the newest
# release — carries PYSEC-2026-1325, a timing side-channel with no fixed
# version available. It is reachable only through the ES* algorithms; we sign
# with HS256 (see JWT_ALGORITHM), which never enters that code. Left in place
# knowingly: this is the one advisory the set still reports.
# bcrypt directly, no passlib. passlib 1.7.4 probes bcrypt.__about__.__version__
# (removed in bcrypt 4.1) and its wrap-bug detection feeds an over-length
# password to the backend, which bcrypt 5 rejects with ValueError — so
# hash_password() raised on every call. app/core/security.py uses the bcrypt
# API directly and emits the same $2b$ hashes.
bcrypt==5.0.0

# Vision
# Both opencv distributions are pinned, at the same version, on purpose.
# ultralytics requires `opencv-python>=4.7.0` with no upper bound, so a plain
# install puts *two* providers of the `cv2` module in site-packages and the
# import resolves to whichever landed last. That is not hypothetical: the same
# requirements file produced cv2 4.11, 4.14 and 5.0 in three environments
# here. OpenCV 5 removed `cv2.CascadeClassifier`, which app/services/safety/
# scanner.py builds at import time, so drawing the 5.0 straw takes the whole
# application down at startup. Pinning both keeps the two copies identical and
# the outcome the same whichever wins.
opencv-python-headless==4.14.0.94
opencv-python==4.14.0.94
